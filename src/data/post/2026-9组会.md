## 1. 仓库中的真实工作边界

结论：当前仓库里真正有成体系实现的 Monkey 系列工作，主要是 3 个：

1. `Monkey`
2. `TextMonkey`
3. `Mini-Monkey`

其中：

- `Monkey` 是根目录主线实现，核心代码在根目录与 `monkey_model/` 下。
- `TextMonkey` 也在同一主线内，和 `Monkey` 共享一部分 Qwen/Qwen-VL 体系代码，但有独立模型实现、训练脚本、Demo 和文档评测入口。
- `Mini-Monkey` 位于 `project/mini_monkey/`，是相对独立的子项目，技术路线和代码组织都与前两者明显不同。
- `MonkeyOCR` 在本仓库内没有对应源码目录，只有 `README.md` 中的论文、权重、外部仓库链接。
- `MonkeyOCRv2` 在当前仓库内完全没有出现，既无 README 条目，也无代码命中。

证据：

- 根 README 将 `Monkey`、`TextMonkey`、`Mini-Monkey` 分别链接到仓库内 `README.md`、`monkey_model/text_monkey/README.md`、`project/mini_monkey`，而 `MonkeyOCR` 链接到外部仓库：`README.md:18-24`、`README.md:28-33`、`README.md:41-46`、`README.md:59-64`
- 仓库目录层面仅存在根目录主线和 `project/mini_monkey/` 子项目，没有 `MonkeyOCR` 目录。
- 全仓检索 `MonkeyOCR` 只命中 `README.md`；检索 `MonkeyOCRv2` 无任何命中。

## 3. 三个主工作的功能定位与技术差异

### 3.1 Monkey

`Monkey` 是这条线的基础版通用多模态模型，重点在提升大多模态模型对高分辨率图像与文本标签的利用能力。

从代码看，它仍然建立在 Qwen/Qwen-VL 体系上：

- `MonkeyLMHeadModel` 继承自 `QWenLMHeadModel`：`monkey_model/modeling_monkey.py:96-145`
- 训练脚本默认模型为 `Qwen/Qwen-VL`：`finetune/finetune_ds_debug.sh:11-25`

从视觉处理看，Monkey 的关键点是同时保留局部窗口与全局图像特征：

- `self.visual.encode(images)` 返回窗口图像与 `images_448`
- 局部 patch 特征与全局特征被拼接后送入模型：`monkey_model/modeling_monkey.py:65-76`

因此它更适合讲成：

- 通用视觉问答 / 图文理解基线
- 强调高分辨率输入与文本相关视觉信息的重要性
- 是后续 TextMonkey 的文档强化路线、Mini-Monkey 的轻量路线的共同出发点

### 3.2 TextMonkey

`TextMonkey` 是沿着“文本密集场景 / 文档理解”方向做深化的版本，定位明显比 Monkey 更聚焦。

README 直接给出的定位与增强点包括：

- OCR-free 文档理解
- 更高输入分辨率下的窗口间信息交互
- 重要视觉特征筛选
- 通过位置相关响应增强可解释性并减少幻觉
- 具备文本定位与 APP Agent 点击潜力

证据见：`monkey_model/text_monkey/README.md:21`、`monkey_model/text_monkey/README.md:83-91`

从代码看，它与 Monkey 的主要区别是视觉编码器独立化：

- `TextMonkeyModel` 里显式替换成 `VisionTransformer(**config.visual)`：`monkey_model/modeling_textmonkey.py:35-39`
- `visual_text.py` / `window.py` 中存在滑窗、cross-window attention、shifted window 等实现：`monkey_model/text_monkey/visual_text.py`、`monkey_model/text_monkey/window.py`
- 训练脚本还额外打开了 `--add_window true --use_global true --resampler true --image_size 896`，说明其训练配置就是围绕高分辨率文档建模设计的：`finetune/finetune_textmonkey.sh:47-54`

因此它更适合讲成：

- Monkey 的文档理解强化版
- 面向场景文本、文档、图表、表格等文本密集场景
- 比 Monkey 更强调文本定位、文档问答、结构化文本理解

### 3.3 Mini-Monkey

`Mini-Monkey` 不是简单的“小号 Monkey”，而是换了一条轻量化与多尺度输入策略并重的路线。

README 直接给出的关键词是：

- 轻量化 MLLM
- MSAC（multi-scale adaptive cropping）
- SCM（Scale Compression Mechanism）
- 在 2B 参数规模下兼顾通用多模态与文档能力

证据见：`project/mini_monkey/README.md:20`

从代码看，它与前两者的差异非常明显：

- 主模型是 `MiniMonkeyChatModel`，不是 Qwen 主线：`project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:38`
- 默认底座是 `OpenGVLab/InternVL2-2B`：`project/mini_monkey/shell/minimonkey/minimonkey_finetune_full.sh:31-39`
- `MiniMonkeyChatModel` 可兼容 `InternLM2 / Llama / Phi3 / Qwen2` 等 LLM 架构：`project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:68-77`
- `demo.py` 中直接实现了动态长宽比匹配、多块裁剪、缩略图补充与二次裁剪拼接：`project/mini_monkey/demo.py:37-73`、`project/mini_monkey/demo.py:76-116`、`project/mini_monkey/demo.py:144-148`
- 模型内部还实现了 token 压缩与 `use_scm` 分支：`project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:218-252`、`project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:396-398`

因此它更适合讲成：

- 轻量化、部署友好
- 通过多尺度裁剪而非单纯堆大模型来提升细粒度视觉理解
- 在小参数量下兼顾通用视觉问答和文档/OCR 类能力

### 3.4 三者对比表

### 3.5 论文关键点到代码实现的细粒度对应

这一节不是再重复“哪个文件负责什么”，而是把论文里常出现的术语，继续压到“哪个配置项、哪个函数、哪一段数据流”。

#### 3.5.1 Monkey / TextMonkey 的共同入口：图片先以特殊 token 形式进入 LLM

这条主线最关键的一点是：图像并不是作为额外 tensor 分支单独传入接口，而是先在文本 prompt 里写成 `<img>...</img>`，再在模型内部根据特殊 token 区间把图片路径解析出来，最后把视觉特征回填到语言模型输入中。

- `demo_textmonkey.py:66-87` 先构造 `"<img>{input_image}</img> {input_str}"`，再调用 `model.generate(...)`
- `demo_textmonkey.py:37` 将 `tokenizer.IMG_TOKEN_SPAN` 设为 `config.visual["n_queries"]`
- `eval/evaluate_vqa_doc.py:499-505` 评测阶段同样把 `IMG_TOKEN_SPAN` 绑定到 `config.visual["n_queries"]`，说明训练、Demo、评测共享同一套“图像 token 长度”约定

这个设计对应论文里的一个核心叙事：视觉信息并不是脱离 LLM 主干单独建模，而是被组织成和文本统一的序列输入，再由 Qwen 主干一起处理。

#### 3.5.2 Monkey：高分辨率图像被拆成“局部窗口 + 全局视图”两路特征

`Monkey` 的论文叙事重点，是“高分辨率图像”和“文本相关细节”不能只靠单张缩放图解决。代码里最直接的落点就是 `MonkeyModel.forward(...)` 的图像解析和特征拼接流程：

- `monkey_model/modeling_monkey.py:55-64` 从 `input_ids` 中定位 `image_start_id` / `image_end_id`，并解码出图像路径
- `monkey_model/modeling_monkey.py:65` 调用 `self.visual.encode(images)`，拿到窗口图像与 `images_448`
- `monkey_model/modeling_monkey.py:68-75` 对每个窗口单独提特征，再对 `images_448` 提取全局特征，最后 `torch.cat([local_feat, global_feat], dim=1)` 拼接

所以如果汇报里要把 Monkey 讲得更“像论文”，更准确的说法不是笼统地说“它支持高分辨率”，而是：

- 局部分支负责保留高分辨率下的小文字、小区域、小目标细节
- 全局分支负责补足整图上下文
- 两路特征最终在送入 Qwen 主干前完成拼接

#### 3.5.3 TextMonkey：关键超参数不是写死在配置类里，而是在训练入口动态覆盖到 `config.visual`

这里有一个很值得在报告里点明的小结论：`monkey_model/configuration_monkey.py:13-65` 里的 `MonkeyConfig` 主要定义的是通用 LLM 配置，本身并没有把 TextMonkey 那些视觉增强项硬编码死。真正决定文档理解行为的，是训练脚本在加载预训练配置后，对 `config.visual` 的二次覆盖：

- `finetune_multitask_dialouge_doc.py:332-345`
  - `config.visual["image_size"] = (training_args.image_height, training_args.image_width)`
  - `config.visual["n_queries"] = training_args.n_queries`
  - `config.visual["add_window"] = training_args.add_window`
  - `config.visual["use_global"] = training_args.use_global`
  - `config.visual["resampler"] = training_args.resampler`
  - `config.visual["r"] = training_args.remain`
- `finetune/finetune_textmonkey.sh:48-54` 进一步给出实际训练值：`image_size=896`、`add_window=true`、`use_global=true`、`resampler=true`

这说明论文里那些增强项，在工程上不是抽象概念，而是被落实成一组可以直接开关和调参的视觉入口。

#### 3.5.4 TextMonkey 的视觉主链：窗口交互、特征压缩、全局补充

`TextMonkeyModel` 和 `MonkeyModel` 的一个重要区别，是它不再只是简单复用原始视觉分支，而是显式换成了文档理解定制的 `VisionTransformer(**config.visual)`：

- `monkey_model/modeling_textmonkey.py:35-38` 初始化独立视觉编码器
- `monkey_model/modeling_textmonkey.py:57-72` 在 forward 阶段解析图片路径并调用 `self.visual.encode(images)`

更细一点看，论文里的几个关键词在 `visual_text.py` 中都有明确落点：

- “窗口建模 / window interaction”
  - `monkey_model/text_monkey/visual_text.py:36-48` 用 `sliding_window(...)` 把图像切成窗口
  - `monkey_model/text_monkey/visual_text.py:417-429` 指定 `window_pos = [2, 6, 24, 46]`，在若干层插入 `CrossWindowAttention`
  - `monkey_model/text_monkey/visual_text.py:443-475` 在 Transformer forward 中重建整图、做跨窗口注意力、再切回窗口
- “重要视觉特征筛选 / token 压缩”
  - `monkey_model/text_monkey/visual_text.py:547-559` 构建 `Resampler` 与可选 `PerceiverResampler`
  - `monkey_model/text_monkey/visual_text.py:638-640` 当 `self.resampler` 打开时，用 `downresampler(local_feat, r=self.r)` 压缩局部特征
  - `monkey_model/text_monkey/resampler.py:107-144` 给出 `PerceiverResampler` 的具体实现，先做 token merge，再用 perceiver attention 聚合
- “全局视图补充”
  - `monkey_model/text_monkey/visual_text.py:631-643` 先生成 `images_448`，再在 `use_global=True` 时把局部特征与全局特征拼接返回

因此 TextMonkey 对论文里“高分辨率文档 + 窗口交互 + 重要特征筛选 + 全局上下文”的落地方式，可以概括成：

1. 先按窗口保留高分辨率局部文本
2. 在部分层引入跨窗口注意力，让不同窗口交换信息
3. 用 resampler / perceiver resampler 压缩高成本视觉 token
4. 再拼一条 448 全局分支，避免只见局部不见整体

#### 3.5.5 `n_queries` 与 `IMG_TOKEN_SPAN` 的真实关系

论文里如果提到“视觉 token 数量”或“query 数量”，在这套实现里最应该对应的是 `n_queries` 和 tokenizer 侧的 `IMG_TOKEN_SPAN`。

- `finetune_multitask_dialouge_doc.py:372-380`
  - 默认先令 `tokenizer.IMG_TOKEN_SPAN = training_args.n_queries`
  - 若启用 `resampler`，则 `IMG_TOKEN_SPAN = training_args.remain`
  - 若再启用 `use_global`，还会再加上一个 `training_args.n_queries`
- `demo_textmonkey.py:37` 与 `eval/evaluate_vqa_doc.py:499` 都说明推理时最终以 `config.visual["n_queries"]` 作为 tokenizer 侧图像 span

这背后的含义是：

- `n_queries` 决定单路视觉特征映射到语言序列时预留多少 token
- `resampler` 会把局部高分辨率分支压到 `remain`
- `use_global` 再额外加上一段全局视觉 token

所以 TextMonkey 里“视觉 token 长度”不是固定值，而是会随局部分支压缩策略和全局分支开关一起变化。

#### 3.5.6 Mini-Monkey：论文里的 MSAC 在代码里就是动态裁剪 + 双阶段拼接

Mini-Monkey 的论文关键词是 `MSAC` 和 `SCM`。这两个词在代码里都能找到直接落点。

先看 `MSAC`：

- `project/mini_monkey/demo.py:22-35` 的 `find_closest_aspect_ratio(...)` 会为原图选择最接近的目标网格比例
- `project/mini_monkey/demo.py:37-73` 的 `dynamic_preprocess(...)` 根据目标比例把图像 resize 后切成多个 `448 x 448` block，并在需要时补一个 thumbnail
- `project/mini_monkey/demo.py:76-116` 的 `dynamic_preprocess2(...)` 再做第二轮裁剪，但会避开与第一次比例完全重复的划分
- `project/mini_monkey/demo.py:144-148` 最终把两轮裁剪结果按 `torch.cat([pixel_values2[:-1], pixel_values[:-1], pixel_values2[-1:]], 0)` 拼起来

也就是说，论文里的“multi-scale adaptive cropping”在实现层面并不是一句口号，而是：

1. 先根据原图长宽比选裁块网格
2. 生成多块局部 patch
3. 追加缩略图保留全局语义
4. 再做第二轮不同尺度裁剪并重新拼接

#### 3.5.7 Mini-Monkey：论文里的 SCM 在代码里就是基于注意力的视觉 token 筛选

再看 `SCM`：

- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:54-55` 先用 `image_size / patch_size` 和 `downsample_ratio` 计算 `num_image_token`
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:218-252` 在 `extract_feature(...)` 里做 `pixel_shuffle + mlp1`，把视觉特征映射到 LLM 隐空间
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:282-283` 与 `335-336` 按 `self.num_image_token * num_patches` 构造 `<IMG_CONTEXT>` 序列
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:396-438` 当 `use_scm=True` 时，先根据早期层注意力估计高价值图像 token，再保留 top-k 部分，最后用筛选后的 `input_embeds` 继续生成

这里特别关键的一点是：Mini-Monkey 的 token 压缩并不是 TextMonkey 那种“先用 resampler 压缩视觉分支，再送入 LLM”，而是直接在生成前根据语言模型早期层注意力，对图像 token 做一次选择性保留。这是它和 TextMonkey 在“降 token 成本”上的重要实现差异。

#### 3.5.8 Monkey / TextMonkey 的主干注入位置：直接覆盖 Qwen 隐藏状态片段

如果老师继续追问“视觉特征最终是怎么进 Qwen 的”，最值得展示的不是视觉编码器本身，而是 `modeling_qwen.py` 里的注入位置。

- `monkey_model/modeling_qwen.py:704-717` 在 `images is None` 时，基础 Qwen-VL 风格逻辑会先从 `input_ids` 里解析图片路径并调用 `self.visual.encode(images)`
- `monkey_model/modeling_qwen.py:780-781` 先把 `input_ids` 映射成标准的词向量 `inputs_embeds = self.wte(input_ids)`
- `monkey_model/modeling_qwen.py:811-813` 若检测到图像特征，则直接执行 `hidden_states[i][a + 1 : b] = images[idx]`

这说明 Monkey / TextMonkey 这条线的融合方式不是“额外 cross-attention 分支再慢慢融合”，而是：

1. 先保留文本序列框架不变
2. 再找到 `<img>...</img>` 在序列中的占位区间
3. 用视觉编码结果直接覆盖这一段隐藏状态
4. 后续所有 Transformer 层都把这段视觉 token 当作序列的一部分继续处理

这也是为什么前面 `IMG_TOKEN_SPAN`、`n_queries` 会这么关键，因为它们本质上决定了这段“视觉 token 插槽”到底有多长。

#### 3.5.9 Mini-Monkey 的主干注入位置：先构造 `<IMG_CONTEXT>`，再替换成视觉 embedding

Mini-Monkey 的做法与 Monkey / TextMonkey 很像，但实现接口更显式，因为它先在 prompt 中扩展出一串 `<IMG_CONTEXT>` 占位 token，再把这些位置替换成视觉特征。

- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:282-283` 与 `335-336` 用 `self.num_image_token * num_patches` 构造图像 token 序列
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:152-167` 在 forward 阶段先拿到语言模型 embedding，再找出 `selected = (input_ids == self.img_context_token_id)`
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:167-177` 用 `vit_embeds.reshape(-1, C)` 覆盖 `input_embeds[selected]`
- `project/mini_monkey/internvl/model/internvl_chat/modeling_minimonkey_chat.py:383-390` generate 阶段同样重复这一替换过程，保证推理时图像 token 真正进入 LLM

因此从架构视角看，Mini-Monkey 的关键不是“视觉塔和 LLM 并列”，而是：

1. 先把图像块数转成 prompt 里明确可数的图像上下文 token
2. 再把这些 token 的 embedding 全部替换成视觉特征
3. 若开启 `SCM`，则在生成前再根据早期注意力结果缩减图像 token

如果把三者放在同一张架构图里，最容易讲清的差异其实是：

- `Monkey`：局部 + 全局视觉特征先拼好，再注入 Qwen 序列
- `TextMonkey`：窗口交互与 resampler 先把视觉表示整理好，再注入 Qwen 序列
- `Mini-Monkey`：多尺度裁块先决定 token 数，再把视觉 embedding 替换进 `<IMG_CONTEXT>` 序列

也就是说，三者的共同点是“都把视觉信息写回语言序列”，差异在于写回之前如何组织、筛选和压缩视觉 token。

### 4.4 可直接贴进 PPT 的每页 bullet 文案

#### 第 1 页：仓库范围与分析对象

- 当前仓库真正有完整实现的 Monkey 工作只有 3 个：`Monkey`、`TextMonkey`、`Mini-Monkey`

- `MonkeyOCRv2` 在当前仓库没有出现，本次不纳入代码分析主线

#### 第 2 页：Monkey 系列的演进逻辑

- `Monkey`：通用高分辨率多模态理解起点
- `TextMonkey`：沿文档 / 文本密集场景继续强化，强调 OCR-free 理解
- `Mini-Monkey`：转向轻量化与多尺度裁剪，在 2B 级规模保持综合能力

#### 第 3 页：Monkey 的论文核心点

- 目标是提升大模型对高分辨率图像与文本标签的利用能力
- 关键问题是单尺度整图输入容易丢失局部细节
- 因此需要同时保留局部细节与全局上下文

#### 第 4 页：Monkey 的代码落点

- `modeling_monkey.py` 会先从 `input_ids` 中解析 `<img>...</img>` 对应的图片路径
- 视觉分支把图像编码成两路特征：局部窗口特征 + `448` 全局特征
- 两路特征拼接后再送入 Qwen 主干，实现“局部细节 + 全局语义”的联合建模

#### 第 5 页：TextMonkey 的论文核心点

- 面向文档、图表、表格、场景文字等文本密集图像
- 重点增强窗口间信息交互、重要视觉特征筛选和定位能力
- 目标是做 OCR-free 文档理解，并降低幻觉

#### 第 6 页：TextMonkey 的代码落点

- 训练入口把 `image_size`、`n_queries`、`add_window`、`use_global`、`resampler` 写入 `config.visual`
- `VisionTransformer(**config.visual)` 负责文档视觉建模主链
- `add_window` 对应跨窗口交互，`resampler` 对应视觉 token 压缩，`use_global` 对应全局视图补充

#### 第 7 页：TextMonkey 的一个关键实现结论

- `n_queries` 不只是普通超参数，它直接关联 tokenizer 侧的 `IMG_TOKEN_SPAN`
- 开启 `resampler` 后，局部分支 token 会压缩到 `remain`
- 开启 `use_global` 后，还会额外拼上一段全局视觉 token

#### 第 8 页：Mini-Monkey 的论文核心点

- 核心关键词是 `MSAC` 和 `SCM`
- 它不是继续放大模型，而是通过更聪明的输入裁剪与 token 压缩提升性能
- 重点是在轻量参数规模下兼顾通用多模态能力和文档能力

#### 第 9 页：Mini-Monkey 的代码落点

- `dynamic_preprocess(...)` 会按长宽比自适应决定裁块网格
- 第一轮裁剪后还会补缩略图保留全局信息，再做第二轮不同尺度裁剪
- 最终把不同尺度 patch 拼接后送入 `model.chat(...)`

#### 第 10 页：Mini-Monkey 的 SCM 落点

- 模型先根据 `num_image_token * num_patches` 构造图像 token 序列
- `extract_feature(...)` 通过 `pixel_shuffle + mlp1` 把视觉特征映射到 LLM 空间
- `use_scm=True` 时，会根据早期层注意力筛选更重要的图像 token，再继续生成

#### 第 11 页：三者横向对比

- `Monkey`：局部窗口 + 全局视图拼接，适合作为系列起点
- `TextMonkey`：窗口交互 + token 压缩 + 全局补充，更适合文档和文本密集场景
- `Mini-Monkey`：多尺度裁剪 + 注意力式 token 筛选，更强调轻量化与部署友好

#### 第 12 页：最终结论

- 本仓库最值得展开讲的主线只有 `Monkey -> TextMonkey -> Mini-Monkey`
- 三者不是简单大小差别，而是视觉信息保留与压缩策略逐步分化
- `MonkeyOCR` 及后续版本只适合做时间线补充，不适合作为本次代码分析主体

#### 可选加一页：视觉特征如何进入 LLM 主干

- `Monkey / TextMonkey`：在 Qwen 的 hidden states 中直接用视觉特征覆盖 `<img>...</img>` 对应区间
- `Mini-Monkey`：先扩展 `<IMG_CONTEXT>` token，再把这些位置的 embedding 替换成视觉特征
- 三者共同点都是“把视觉写回语言序列”，差异在于写回前如何组织和压缩视觉 token

### 7.4 数据处理与输入格式对照表

| 论文关键点 | 工程化含义 | 代码落点 | 汇报时怎么说 |
| --- | --- | --- | --- |
| 统一的图文交错格式 | 图片在文本流中表现为特殊的占位符或标签 | `finetune_multitask_dialouge_doc.py:153-162` | Monkey / TextMonkey 把图片路径写在 `<img>...</img>` 之间，完全复用语言模型的 tokenizer 流程 |

### 7.5 三者最值得老师追问时展开的差异

| 比较维度 | Monkey | TextMonkey | Mini-Monkey |
| --- | --- | --- | --- |
| 主要目标 | 高分辨率通用多模态理解 | 文档 / 文本密集场景强化 | 小模型下保住细粒度能力 |
| 视觉组织策略 | 局部窗口 + 全局图拼接 | 窗口交互 + resampler + 全局补充 | 多尺度裁剪 + SCM |
| token 压缩方式 | 主要靠视觉组织改善表示 | 视觉侧先做 resampler 压缩 | 生成前按注意力筛 token |
| 主干注入方式 | 写回 Qwen 图像区间 | 写回 Qwen 图像区间 | 替换 `<IMG_CONTEXT>` embedding |
| 最适合一句话概括 | 系列起点 | 文档增强版 | 轻量化路线 |
